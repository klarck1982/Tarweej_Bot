## السبب الجذري المشترك

انتقالات حالة الطلب تُكتب بنمط **«اقرأ ثم اكتب»** دون شرط:

```python
o = await repo.get(order_id)            # 1) قراءة: الحالة = submitted
if o["status"] != "submitted": return
...                                     # ← هنا قد يغيّر طرف آخر الحالة (استرداد/إلغاء)
await repo.update(order_id, status=...) # 2) كتابة: UPDATE ... WHERE id=$1  (لا تتحقق من الحالة!)
```

و`orders.refund()` نفسها محمية جيداً (`FOR UPDATE` + سقف المسترد)، لكنها **لا تعيد التحقق** من الحالة التي فحصها المستدعي قبل دخول القفل.

## 🔴 1. استرداد الأدمن أثناء إرسال الطلب إلى نور ← العميل يسترد والحملة تعمل

**المكان:** `services/orders.py` في `submit()` السطر 215 وما بعده.

**السيناريو:**
1. طلب Meta بحالة `paid` ينتظر إعادة المحاولة (مثلاً «رصيد نور غير كافٍ»).
2. المجدول يستدعي `submit()` ويرسل الطلب إلى نور، والطلب يستغرق ثوانٍ.
3. في هذه الثواني يضغط الأدمن «↩️ استرداد» فيُعاد المال للعميل وتصير الحالة `refunded`.
4. يصل رد نور، فتكتب `submit()` الحالة `submitted` مع `nour_id` **فوق** `refunded`.

**النتيجة المؤكَّدة (مرتان من مرتين):**
```
final: {'status': 'submitted', 'nour_id': 'N1', 'refunded_usd': 13.50, 'price_usd': 13.50}
❌ العميل استرد 13.50 والحملة أُرسلت لنور N1
```
**الأثر:** خسارة كاملة لتكلفة الحملة من رصيدك عند نور. وبما أن `refunded_usd` بلغ السعر كاملاً، لن تسترد المزامنة اللاحقة مرتين، لكن الخسارة وقعت فعلاً.

**السكربت:** `tests/_sim/review2/repro_submit_refund.py`

## 🟠 2. إلغاء العميل ⟷ نشر/بدء الأدمن ← استرداد كامل مع منشور منشور

**المكان:** `partner_posts.cancel_by_user` مع `publish`/`schedule`، و`design.cancel_by_user` مع `start`.

**السيناريو:** `cancel_by_user` يتحقق من `status == submitted` **خارج** القفل، وفي اللحظة نفسها يضغط الأدمن «🔗 تم النشر». النتيجة: الحالة `active` مع استرداد كامل، أو العكس.

**النتيجة المؤكَّدة:**
```
مثال tg_post: status=active refunded=13.50
حالات (مُسترد + ما زال مفتوحاً للعمل): {'design': 0, 'tg_post': 4} من 30 لكل نوع
```
**الأثر:** القناة الشريكة نشرت الإعلان (وتستحق أجرها) والعميل استرد كامل المبلغ. التصميم يحمل النمط نفسه، ولم يظهر في هذا التوقيت فقط.

**السكربت:** `tests/_sim/review2/repro_cancel_vs_start.py`

## 🟠 3. الاعتماد التلقائي ⟷ طلب تعديل مدفوع ← العميل يدفع ثم يُغلق الطلب

**المكان:** `design.approve()`، الذي يستدعيه المجدول في `auto_approve_due`، أو الأدمن بالنيابة، أو العميل، مع `design.request_revision()`.

**السيناريو:** العميل يطلب تعديلاً إضافياً مدفوعاً (يُخصم 30% من السعر) في لحظة انتهاء مهلة الاعتماد التلقائي. `request_revision` يخصم الرسم ويضبط الحالة `needs_revision`، ثم يكتب `approve()` (الذي قرأ الحالة `delivered` قبل ذلك) الحالة `completed` فوقها.

**النتيجة المؤكَّدة:**
```
رسم تعديل مخصوم + الطلب مكتمل: 39/40
```
**الأثر:** العميل دفع رسم التعديل، والطلب أُغلق ولن يصل التعديل إلى المصمم. يحدث أيضاً لو ضغط العميل «✅ اعتماد» و«✏️ تعديل» بسرعة.

**السكربت:** `tests/_sim/review2/repro_approve_vs_revision.py`

## 🟡 4. إرسال الطلب نفسه إلى نور مرتين

`due_for_retry()` تختار الطلبات التي `next_retry_at IS NULL`، أي الطلب الذي دُفع للتو ويرسله المعالج **الآن**. لذلك قد يرسل المجدول الطلب نفسه في اللحظة نفسها. يحدث ذلك أيضاً مع زر الأدمن «إعادة الإرسال»، أو عند تداخل نسختين من البوت أثناء النشر على Render.

**مؤكَّد:** `create_campaign calls for one order: 2`

**الأثر الحالي:** محمي **فقط** بمفتاح `Idempotency-Key` عند نور. إن لم تحترمه نور فستُنشأ حملتان.

## ✅ ما رُوجع ووُجد سليماً

- **التحقق في Cpanel:** HMAC مع `compare_digest`، وانتهاء `auth_date` بعد ساعة، والتحقق من ADMIN_IDS (401/403)، وحد 256KB لجسم الطلب.
- **Webhook:** يُستخدم `secret_token`، ومسار `/health` لا يلمس القاعدة.
- **الشحن:** `approve`/`reject` يعملان بتحديث شرطي `WHERE status='pending'`، فلا اعتماد مزدوج.
- **دفتر الحركات:** كل قيد يمر عبر `lock_user`، ولا فروقات في 500 إجراء محاكاة.
- **`refund()`:** قفل السطر مع سقف `refunded_usd ≤ price`، فلا استرداد مزدوج ماليّاً.
- **الترحيلات:** قفل استشاري (`pg_advisory_lock`)، فلا تتصادم نسختان أثناء النشر.
- **التذاكر وFSM:** التحديثات شرطية أو مقفلة.
- **الاشتراكات المجدولة (المرحلة 4):** الترتيب والمهلة والإيقاف كلها سليمة.
- **المهام الخلفية:** محفوظة المرجع، فلا تُجمع كنفايات.
